## Phase Scope Note (read first)

**Phase 5 (Session Refresh) ships almost no new visual surface — its contract is primarily an
*interaction* contract.** Per ROADMAP.md Phase 5: the shared axios instance
(`frontend/src/services/api.js`) gains a single-flight 401 response interceptor (plan 05-01),
verified by a manual protocol (05-02) and a regression pass (05-03). The only files this phase may
touch in `frontend/` are `src/services/api.js` (interceptor) and `src/views/Login.vue` (one new
session-expired notice — see Copywriting). **No new views, no new components, no token, type,
color, or stylesheet changes.**

The user-visible guarantees this phase must uphold (ROADMAP Phase 5 Success Criteria, cited as
roadmap success criteria — no phase CONTEXT.md exists):

1. A user working continuously past the 15-minute access-token TTL **never sees the login page** —
   the original request succeeds after one silent `POST /auth/refresh`. The refresh is *invisible*:
   no spinner, no banner, no navigation, no lost form state.
2. N parallel requests hitting 401 at the same moment trigger **exactly one refresh** (single-flight)
   — from the user's perspective, nothing flickers and no view re-renders.
3. When the refresh cookie is dead, the user is redirected to login **exactly once** — and the
   refresh request itself is never retried (ROADMAP criterion quoted verbatim) — landing there with
   a clear, non-alarming explanation (the new `.alert.warn` notice), never in a `/login` ⇄ dashboard
   bounce loop. *Addendum beyond the roadmap text:* the notice copy itself, specified below.
4. `npm run build` passes; `services/api.js` imports no router (no import cycle); **no per-view 401
   handling appears anywhere.**

**Consequences for downstream consumers:**
- `gsd-planner`: plan tasks may only create/modify `frontend/src/services/api.js` and
  `frontend/src/views/Login.vue` within `frontend/`. Success criteria are proven by the manual
  protocol (plan 05-02), not by UI screenshots.
  **Alignment warning (checker recommendation):** ROADMAP plans 05-01…05-03 name only
  `frontend/src/services/api.js`. The `Login.vue` notice + `?reason=session-expired` mechanism is
  specified *here*, not in the roadmap plan text. When `/gsd-plan-phase 5` runs, the plan files must
  carry this spec's two-file boundary verbatim — otherwise plan-vs-roadmap will read as drift.
- `gsd-executor`: the Interaction Contract section below is normative — implement it verbatim.
- `gsd-ui-checker`: dimensions are evaluated against (a) the one new notice on Login and
  (b) *invisibility* of the refresh everywhere else. Sections marked "inherited / unchanged"
  restate the approved Phase 1 baseline (01-UI-SPEC, approved 2026-09-23) — this phase must not
  contradict or drift from it.

**Upstream sources:** no phase-level CONTEXT.md and no phase-level 05-RESEARCH.md exist for this

## Copywriting Contract

**Two user-facing strings this phase owns** (the rest of the app's copy is untouched). Repo voice
is Portuguese; strings are locked verbatim — no plan may rephrase them.

| Element | Copy |
|---------|------|
| Primary CTA | not applicable — no new screens or forms; existing CTAs unchanged (`Entrar`, `Entrando…`, `Criar rascunho`/`Salvando…`, etc.) |
| Session-expired notice (NEW — Login, `.alert.warn`, `role="status"`) | `Sua sessão expirou. Entre novamente para continuar.` |
| Empty state heading | not applicable — no list/media surface is created or modified |
| Empty state body | not applicable |
| Error state | No new global error UI. Existing behavior locked: Login failure keeps `e.response?.data?.error \|\| 'Falha no login'` in `div.alert.error[role=alert]`; other views keep their existing per-view `err` alerts. The interceptor adds **zero** new error rendering outside Login. |
| Destructive confirmation | none — Phase 5 performs no destructive product actions (the redirect is a session event, not a user action) |

**Navigation contract (locked):**
- Session death (refresh rejected) → exactly one `window.location.assign('/login?reason=session-expired')`.
  The `reason` query param is how `Login.vue` decides to render the notice
  (`new URLSearchParams(location.search).get('reason') === 'session-expired'`). Plain
  `/login` visits (manual navigation, login required by router guard) show **no** notice.
- Success criterion "redirected to login exactly once" is honored mechanically: the interceptor
  guards with a module-level "already redirecting" flag so N concurrent rejected retries issue one
  `assign` call — never a loop, never stacked navigations.
- After the notice renders, the normal login flow is fully usable in the same render: if a login
  attempt then fails, the `.alert.error` shows below/alongside the `.alert.warn` — the warn notice
  is never used to display credential errors, and credential errors never use `.alert.warn`.

## Interaction Contract (Phase 5 core — normative for gsd-executor)

These rules are the phase's real deliverable. Sources: SES-01 (REQUIREMENTS.md), ROADMAP Phase 5
success criteria, PITFALLS.md Pitfall 3 + UX-pitfalls table.

1. **Placement.** The 401 response interceptor is installed **only** on the shared axios instance
   exported by `frontend/src/services/api.js`. No interceptor on any other instance; no per-view
   (`view`-level) 401 handling anywhere; `api.js` imports **no** router module (import cycle —
   `window.location.assign` is the only navigation mechanism).
2. **Silent refresh.** On a 401 response where `config._retry` is falsy: set `config._retry = true`,
   await the **single shared refresh promise** (one in-flight `POST /auth/refresh` exists globally;
   every concurrent 401 awaits the same promise), then replay the original request once with its
   original config (`withCredentials` preserved). To the user this is invisible: **no spinner, no
   skeleton, no banner, no route change, no form-state loss** — view-level loading refs
   (`Entrando…`/`Salvando…`) behave exactly as they do today.
3. **Retry at most once.** A replayed request that 401s again rejects straight through — it must
   never re-enter the refresh path (`_retry` guard). The refresh request itself is **never retried**.
4. **Refresh failure → one bounce.** Refresh rejected (dead 7-day cookie / `Sem refresh`): clear the
   auth store user, reject the pending request, set the redirecting flag, and call
   `window.location.assign('/login?reason=session-expired')` exactly once. No fallback to
   `router.push`, no retry of refresh, no error toast.
5. **Only true session death redirects.** The interceptor refreshes/redirects **only on HTTP 401**.
   Network errors, timeouts, and 5xx reject through with no refresh and no redirect (transient
   failures must not bounce a healthy user to login — PITFALLS UX rule). **403 never triggers
   refresh or redirect** — in particular `PASSWORD_CHANGE_REQUIRED`-style 403s route through
   untouched (full forced-change UX is SES-02 / Phase 8, but the interceptor must not swallow it
   here). 429 from `/auth/refresh` likewise rejects without retry.
6. **No new global state UI.** The interceptor renders nothing. It does not log token/cookie
   values (PITFALLS security rule) and does not touch `tokens.css`/`base.css`.
7. **Manual verification is the DoD** (plan 05-02): TTL dropped to ~10s → exactly one
   `POST /auth/refresh` per expiry in the network tab while the current view stays put; N parallel
   401s → exactly one refresh; deleted refresh cookie → exactly one navigation to
   `/login?reason=session-expired` showing the locked notice; `cd frontend && npm run build` green.
